Review from pullspace: comments, replies and verdicts

pullspace can now write back to a pull request: comment on a line of the diff, reply to a thread, comment on the discussion, and submit a review that approves, requests changes or just comments, with its held line comments sent in the same request.

Why

Until now pullspace could only read. A reviewer read the diff here and then went to github.com to say anything, which put the most important step of a review back in the tool pullspace exists to replace. Write support was the first item under "Upcoming" in the README.

Two constraints shaped it. There is no server, so every write is the browser calling api.github.com with the pasted token, and a token that is read-only has to be explained rather than failed on. And a line comment is only a place in a particular diff, so the app has to offer comments only where GitHub will take them.

Reading order

  1. github.rs — the writing section: Side, Verdict, LineNote, and the four calls. Start with post_json and write_error, which every write goes through: no token means no request, a 403 that isn't an empty budget is GitHub's own reason, and a 404 is explained as missing write access. review_body is split out so its JSON is tested without a network.
  2. github.rs — the new Comment fields: id, reply_to, side and outdated, which are what a reply is addressed to and what places a thread under the right line. outdated is "has a path but GitHub sent a null line".
  3. drafts.rs — Pending: a review being written, kept per pull request in localStorage like the viewed marks. Note commit(): notes written across a push leave commit_id to GitHub rather than guessing.
  4. ui/review.rs — Talk, then talk: which lines get a + (anything not in a contracted gap, which is GitHub's own diff with 3 lines of context) and which have something hanging under them. talk runs in a memo in the viewer, so typing into the review box does not redraw the diff.
  5. viewer.rs — split_add and the t: &Talk parameter threaded through render_inline/render_split: the + and the threads go into rows that are plain functions, not components, so a 6,000-line file still pays nothing for lines with nothing under them.
  6. ui/review.rs — NOTE_JS and adds: one page-side click listener for every +, like the line-number one in viewer.rs, reporting the side and line; the file is whichever is open.
  7. ui/review.rs — hold, send_line, send_review: holding a note, sending one now or as a reply, and submitting the review. On success a review removes only the notes it actually sent, and conversation::reload refetches without the Loading blink.
  8. LineThread and ReviewBox: the two places a reader writes: under a line, and at the foot of the conversation. Then the three new signals on St, the effect that loads drafts as a PR opens, and the listener in App.

The map pages for src/backend and src/ui were rewritten where they described pullspace as read-only (the ui page gains a "Writing back" paragraph and a gotcha about keyed components in release builds). The root and src pages only lose "write support" from their plans.

Decisions

Held notes live in the browser, not in a pending review on GitHub. The REST API can only create a pending review whole; adding a comment to one afterwards is a GraphQL mutation per comment, and a pending review left on GitHub by a closed tab is litter on somebody else's pull request. Kept in localStorage, a half-written review survives a reload and goes out as one request, the way github.com sends one.

The review state is global and keyed by pull request, not per space. drafts, composing and writing are seeded with literals, not registered in held!. Two spaces on one pull request are writing one review, and composing carries its pull request and path, so a box opened on one never shows on another.

One write in flight, app-wide. Writing is a single signal and every send button is disabled while it is Busy. A second press during a write is far more likely a double click than a second thought, and a doubled review is visible to everyone on the PR.

Comments are offered only on lines GitHub's diff has. Lines opened out of a gap are real code but GitHub answers a comment on them with a 422. difftool::CONTEXT is 3, the same as GitHub's, so "not in a gap" matches GitHub's hunks without asking it.

Replies and "Comment now" post immediately; new line comments are held by default. A reply only makes sense in the thread it answers, and the REST review endpoint cannot carry replies. A new comment is usually part of a review, so ⌘Enter holds it.

Approve and Request changes are disabled on your own pull request instead of letting GitHub refuse with a 422, since that refusal would come after somebody wrote the summary.

Risks

No write has been sent to GitHub from this branch. The request bodies and error parsing are unit-tested, and the UI was mounted headlessly, but the first real comment, reply and review will be the first proof that the endpoints, headers and CORS behave. Try it on a scratch PR first. A wrong body shows as a red box under the button with GitHub's message; nothing is lost, because held notes and the typed text stay until a send succeeds.

Our diff and GitHub's can disagree about hunks. The diff is computed locally (similar) and GitHub uses git's. Where they place a change differently, a + can appear on a line GitHub will not take. That comment fails with "line could not be resolved", and because a review is one request, the whole review fails with it until that note is deleted. The same goes for notes whose lines a later push rewrote.

Read-only tokens. Existing users may have fine-grained tokens with read-only pull requests. They will see a 404 explained as missing write access; the sign-in hint now says what to grant.

Two windows on one pull request. Drafts are saved read-modify-write, so two windows on different PRs don't clobber each other, but two windows on the same PR hold separate in-memory copies, and the last to save wins.

Not changed

No merging, no editing or deleting comments already on GitHub, no multi-line comments (start_line), and no commenting from a single commit of a PR: its line numbers are that commit's diff, which GitHub would not map onto the PR. Line comments in the conversation list still jump to the file in Source view, as before. refused and get_json are untouched: reads keep their messages, and writes have their own.

How it was checked

  • cargo fmt --check, cargo clippy --all-targets -- -D warnings, cargo test (328 pass, including new tests for the review JSON, both shapes of GitHub's errors list, the 404 explanation, reply/side/outdated parsing, and the drafts book), and cargo check --target wasm32-unknown-unknown in both debug and --release. Release caught three keyed components moving what their keys read.
  • NOTE_JS extracted and driven under node with DOM stubs: sends [side, line] for a +, ignores bad sides, bad numbers and other clicks, and does not stack listeners when re-run.
  • The real App mounted headlessly in a scratch copy (not in the repo) on a fixture PR: 15 +s on a file with two changes (exactly the two hunks), an existing thread with its reply under line 10, an outdated comment kept out of the diff, a held note under a deleted line in both inline and split views, a reply box opening inside its thread, verdicts disabled on the author's own PR, and nothing to click when signed out. Inline and split views were screenshotted from its output.
  • Not checked: any request against the real API, and the app in a real browser.
