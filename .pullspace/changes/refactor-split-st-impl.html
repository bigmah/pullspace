Split impl St across files by concern

This turns ui/app.rs into ui/app/ and moves the 1,200-line impl St block out into five files, one per thing the methods do, without changing a method or a call site.

Why

app.rs is the most-changed file in the repository (42 commits) and was 2,960 lines long. Most of it was one impl St with about 65 methods, grouped only by comment headers that had drifted: the "opening a diff back up" section also held has_file, forget_contents and open_at, and "reading a summary" also held closing tabs. Finding the code for Back, or for what happens when a PR opens, meant knowing roughly which thousand lines to look in.

Reading order

  1. mod.rs: the new submodules. Everything else in mod.rs (the state types, St, App, the tests) is the old file unchanged. The only other edit is the include_str! path for the stylesheet, which gained a ../.
  2. mod.rs: what stayed in impl St: the small accessors (token, viewer, bump_tick, prefs, generation). They are what every other file leans on.
  3. workspace.rs: enter: entering, clearing and closing a workspace, routes and places, and forgetting what a closed one held. It also takes collapse_tree, which sits next to reset_tree_folds.
  4. history.rs: the trail and the tabs: open file, Back/Forward, the tab strip, reopen and close, then the reader and summary panes. This is the one file whose method order changed. Tab methods that had drifted under other headers now sit under "the tabs".
  5. stepping.rs, gaps.rs and marks.rs: next file, change or find hit; diff expansions; files marked read. Each is a straight move.

Decisions

Several impl St blocks, not sub-structs of signals. Grouping the ~80 signals into St.nav, St.find and so on would also organise the state, but it would touch the held! list in spaces.rs and every st.foo read across ui/. Extra impl blocks change no call site.

Visibility is kept as tight as it was. Private methods become pub(super), which reaches app and its children and nothing more. stow was pub(super), reachable from all of ui, and is now pub(in crate::ui) so it keeps that reach from one level deeper.

marks.rs, not viewed.rs. mod.rs already imports backend::viewed, and a child module with the same name would clash with that import.

Risks

Low: the moved code compiles to the same items. A normalised comparison of the old file against the new files (whitespace, pub(…) and section headers stripped, lines sorted) differs only in the path fixes listed above and one line rustfmt wrapped.

A new method now needs a home. Adding it to mod.rs out of habit would slowly grow the old file back. The src/ui/ page lists what each file is for.

Not changed

The St struct, held! and the App component. App is still about 550 lines in mod.rs, and splitting its effects out is a separate job. The old guide feat-summaries.html links a line in app.rs and is left as written for its own PR.

How it was checked

  • cargo test: 322 passed, the same as main.
  • cargo clippy --all-targets: no warnings.
  • cargo build --target wasm32-unknown-unknown --release: builds. This is the build that catches the rsx key/clone trap.
  • cargo doc: no new warnings.
  • The app itself wasn't run in a browser.
